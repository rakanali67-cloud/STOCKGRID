> Version 1.0 | 2026-07-31

## Connection & Configuration

| Environment Variable | Default | Purpose |
|---|---|---|
| `STOCKGRID_DB_HOST` | `localhost` | MySQL server host |
| `STOCKGRID_DB_USER` | `root` | MySQL username |
| `STOCKGRID_DB_PASSWORD` | *(required)* | MySQL password |
| `STOCKGRID_DB_NAME` | `stockgrid` | Database name |
| `STOCKGRID_DB_POOL_SIZE` | `32` | Connection pool size |

Set these in a `.env` file at the project root (loaded automatically via `python-dotenv`).

## Schema Overview

StockGrid uses **one MySQL database** with **~30 tables** across six functional areas.

| Area | Tables |
|---|---|
| Identity | `users`, `roles`, `login_attempts`, `password_reset_tokens`, `email_verification_tokens`, `user_invitations` |
| Inventory | `products`, `categories`, `suppliers`, `stock_movements`, `stock_adjustments`, `warehouses`, `locations`, `stock_reservations` |
| Procurement | `purchase_orders`, `po_items`, `purchase_receives`, `purchase_receive_items` |
| Sales | `customers`, `sales_orders`, `sale_items`, `invoices`, `invoice_items`, `sales_receipts`, `receipt_items`, `sales_returns`, `return_items` |
| Finance | `bills`, `bill_items`, `payments_made`, `payment_bill_applications`, `payments_received`, `payment_invoice_applications`, `credit_notes`, `credit_note_items`, `vendor_credits`, `vendor_credit_items`, `vendor_credit_applications`, `vendor_credit_refunds` |
| System | `organization`, `currencies`, `app_settings`, `payment_terms`, `audit_logs`, `reorder_rules` |

## Key Table Relationships

```
products ──┬── categories        (product belongs to one category)
           ├── suppliers          (product has a default supplier)
           ├── stock_movements    (every IN/OUT records a row here)
           ├── stock_reservations (qty held for unshipped sales orders)
           └── reorder_rules      (per-product reorder configuration)

purchase_orders ── po_items ── products
                └── purchase_receives ── purchase_receive_items

sales_orders ── sale_items ── products
             └── customers

invoices ─── invoice_items ── products
          └── payment_invoice_applications ── payments_received

bills ────── bill_items
          └── payment_bill_applications ── payments_made

vendor_credits ── vendor_credit_items
               ├── vendor_credit_applications ── bills
               └── vendor_credit_refunds
```

## Sequence Number Prefixes

All document numbers are generated by `core/sequences.py → next_number()`.

| Module | Prefix | Table | Column | Example |
|---|---|---|---|---|
| Invoices | `INV` | `invoices` | `invoice_number` | `INV-000001` |
| Sales Receipts | `SR` | `sales_receipts` | `receipt_number` | `SR-00001` (pad=5) |
| Sales Returns | `RTN` | `sales_returns` | `return_number` | `RTN-000001` |
| Credit Notes | `CN` | `credit_notes` | `credit_note_number` | `CN-000001` |
| Bills | `BILL` | `bills` | `bill_number` | `BILL-000001` |
| Vendor Credits | `VC` | `vendor_credits` | `vc_number` | `VC-000001` |
| Purchase Receives | `GRN` | `purchase_receives` | `receive_number` | `GRN-000001` |
| Payments Received | `PMT` | `payments_received` | `payment_number` | `PMT-000001` |
| Payments Made | `VPMT` | `payments_made` | `payment_number` | `VPMT-000001` |
| Sales Orders | `SO` | `sales_orders` | `so_number` | `SO-2026-000001` (year-based) |

> `VPMT-` (Vendor Payment) is intentionally different from `PMT-` (customer receipt) to prevent number collisions.

## Common Patterns

### Soft Delete
Tables that support soft delete have a `deleted_at DATETIME NULL` column. Records are never physically deleted — they are excluded from queries with `WHERE deleted_at IS NULL`.

Affected tables: `products`, `categories`, `suppliers`, `customers`, `users`, `sales_orders`, `purchase_orders`.

### Document Status Lifecycles

| Document | Status Flow |
|---|---|
| Sales Order | `PENDING` → `CONFIRMED` → `SHIPPED` (or `CANCELLED`) |
| Purchase Order | `DRAFT` → `SENT` → `PARTIAL` → `RECEIVED` |
| Invoice | `DRAFT` → `SENT` → `PARTIAL` → `PAID` (or `VOID`) |
| Bill | `DRAFT` → `OPEN` → `PARTIAL` → `PAID` (or `VOID`) |
| Credit Note | `DRAFT` → `OPEN` → `PARTIAL` → `APPLIED` (or `VOID`) |
| Payment Made | `DRAFT` → `PAID` (or `VOID`) |
| Sales Return | `DRAFT` → `PENDING` → `APPROVED` → `RECEIVED` → `CREDIT_ISSUED` → `CLOSED` |

### Audit Logging
Every create/update/delete goes through `routes/audit_utils.py → audit()`, which writes to `audit_logs` with the user, action, entity type/id, and JSON before/after values.

### Migration Pattern
Each blueprint file has a `_migrate()` function guarded by a `_migrated` bool. `migrations/__init__.py → run_all()` calls them in dependency order at app startup. These functions are idempotent: they use `CREATE TABLE IF NOT EXISTS` and check `information_schema.COLUMNS` before `ALTER TABLE`.

---

## Adding a New Table

1. Add `CREATE TABLE IF NOT EXISTS ...` to the relevant route file's `_migrate()` function.
2. Run `migrations.run_all()` is called automatically at startup — no separate migration command needed.
3. If the table needs a sequence-numbered primary document ID, use `core/sequences.py → next_number(prefix, table, column)`.

## Resetting the Database (Development Only)

```bash
mysql -u root -p -e "DROP DATABASE IF EXISTS stockgrid; CREATE DATABASE stockgrid CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
python app.py   # migrations run automatically, all tables recreated
```
